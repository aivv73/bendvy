## AppA and owned-payload handoff

AppA installs an optional array/scalar bundle, observes pending installation,
flushes explicitly and registers its actual affine captures and systems.

| Operation | Required retained behavior |
| --- | --- |
| Failed explicit replacement | Return the actual incoming array in a recovery record. |
| Withdraw and retry | Install that same returned owner and retain the displaced original array. |
| Publish the displaced array | Transfer the actual owner into an owned event. |
| Read and update a scalar | Preserve the registered Reader and scratch owners while using the event's projected value. |
| Three schedule updates | Preserve Counter writes, scalar query updates and the independent resource capture. |
| True, false, true condition | Skip only the selected query's middle invocation and preserve its cursor and capture. |
| Repeated passive inspection | Return the same actual World and Inspector instance without clock or cursor advancement. |

The named explicit recovery facility has a live user operation. It remains
separate from ordinary scheduling. Its modern component adapter validates the
actual World handle, uses full-origin columns and physical offsets, records
actual payloads and stamps, refreshes replacement caches and restores saved
stamps during undo. This does not make scheduled bodies transactional.

Publisher and Reader remain distinct registered owners. The original three
gameplay systems retain their actual Compilation, Local and capture packs.
Counter writer precedes Counter reader through the explicit dependency. Authored
feature grouping must not substitute an execution policy for that dependency.
Bootstrap owners, original Context, command queues, both binding inventories and
the event Reader remain outside the gameplay World scope.

The existing scenario observes query calls `[1]`, `[1]`, `[2]`, captured values
`[57,67]`, `[57,67]`, `[88,98]`, scalar `31`, `31`, `35`, Counter `[21,22]`,
resource capture progression and every displaced Counter owner. These are
source-bound expected observations, not a new runtime result for the migration.

## AppB and graph ownership

AppB's domain operation installs three array/scalar bundles, queues independent
Parent and Link relationships, reparents one entity and inspects the result.
Its command author has the structural and relation grants from the same closed
declaration. Handles must come from three actual reservation results.

Before explicit flushes, authored commands stay pending. Flushes consume actual
unapplied IDs and preserve returned owners and remaining IDs. A framework boundary
peer supplies scheduling without adding gameplay behavior. AppB introduces no
event-reader or machine-transition step.

The Phase resource starts at current `1`, pending next `2`, revision `0` and keeps
that pending intent through inspection. Reparenting updates the hierarchy inverse
without changing the independent Link descriptor. Repeated projections agree.
Diagnostic array reads validate namespace and live full handles before physical
lookup, return each actual array twice and preserve cache and lifecycle stamps.
They remain distinct from the public passive Inspector capability.

## Qualification and scope

Both applications retain real Factory provisioning, nominal schema identities,
arbitrary affine payloads, protected resource evidence and genuine returned
owners. No old executor wrapper is an acceptable implementation of either entry.

The [historical migration and backend observations](https://github.com/dearlordylord/bendvy/blob/431266bac456c5e3cf2f2bbf97d512ae1e7f5a65/docs/design/execution-original-applications.md)
record earlier complete observations and their source bindings. They do not
qualify the current changed source. Each application must be checked through its
actual selected operations. Finite rendered outputs do not prove universal
preservation, complete runtime snapshots or worker placement. No new mathematical
law or proof is claimed.
